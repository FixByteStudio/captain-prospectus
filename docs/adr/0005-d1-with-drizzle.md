# ADR-0005: D1 with Drizzle ORM

- Status: accepted — amended by [ADR-0033](0033-rollout-rules-wait-for-protected-data.md): the expand → migrate → contract rule applies only once the data stage is protected
- Date: 2026-09-21

## Context
We want SQLite semantics, zero cost, no cold start, and typed queries.

## Decision
We will use Cloudflare D1 as the only database, accessed through Drizzle ORM. The schema lives in `src/worker/db/schema.ts`; migrations are generated by `drizzle-kit generate` into `drizzle/` and applied with `wrangler d1 migrations apply`.

## Alternatives considered
| Option | Why not |
|---|---|
| Turso | Good, but a second vendor once we are on Cloudflare |
| Raw SQL | Loses typing between schema and queries |
| Kysely | Fine, but Drizzle also generates migrations |

## Consequences
- D1 limits apply: **max 100 bound parameters per statement** (inserts must be chunked), single-writer database.
- Migrations must be backward compatible with the currently deployed Worker, because they run before the new code ships (expand → migrate → contract).
- Generated migration files are not edited after merge.
- A hot multi-row insert may use `insertOrIgnore` (`src/worker/db/client.ts`) instead of Drizzle's builder, which costs ~1 µs of Worker CPU per bound value (GH #449). It reads table and column names from the schema and takes the table's insert type, so it stays typed; use it only where a measurement shows the builder over budget.
