- (capability) CAP-1 users roster managed by admins on an Agents page: create, rename, change role, deactivate (never delete); last active admin protected; deactivation deletes sessions and unused codes; deactivated agent's prospects stay assigned and are flagged
- (capability) CAP-2 agent enrols a device with an admin-generated one-time code: 8 Crockford base32 chars, 15 min, single use, typed in-app (iOS home-screen cookie jar rules out links)
- (capability) CAP-3 admin signs in with a generated passphrase shown once and regenerable, never admin-chosen; or enrols a device with a code made from another of their signed-in devices
- (capability) CAP-4 one /login page and POST /api/auth/login, zod/mini union on kind code|passphrase; kind names credential never role; code field default plus Accès administrateur switch
- (capability) CAP-5 D1 sessions: random token in __Host- cookie, hash stored, device label, sliding expiry 90d agent / 30d admin, last_seen_at written <=1/h, every /api request looks up session + active user; per-device revoke
- (capability) CAP-6 break-glass: OWNER_EMAIL var + BREAK_GLASS secret typed in passphrase field, timingSafeEqual, creates/reactivates owner as active admin and opens a session; bootstraps first admin
- (capability) CAP-7 brute force: login_attempts per IP per 15-min window, refuse after 10 failures until window ends; not the rate-limiting binding (no price/free availability, per-location, eventually consistent)
- (capability) CAP-8 CSRF: SameSite=Strict plus Origin check on every non-GET /api request
- (capability) CAP-9 local dev keeps DEV_USER_EMAIL localhost-only; role read from users, filled by seed
- (capability) CAP-10 nightly sweep deletes expired codes, sessions and login_attempts rows in the existing daily retention cron (ADR-0023, which already sweeps positions per ADR-0028)
- (capability) CAP-11 roster consumers read users: assign menu GET /api/admin/agents and ADR-0028 position gate move from ADMIN_EMAILS/AGENT_EMAILS to users.role
- (capability) CAP-12 client: 401 opens /login; outbox kept, cached round dropped (INVARIANT 5 unchanged); Access logout link, ?reconnect=1 marker and /cdn-cgi/ denylist exception removed
- (capability) CAP-13 three-phase cutover: phase 1 session with Access-JWT fallback; phase 2 agents enrol, owner revokes Access tokens and deletes the app; phase 3 PR removes JWT check, jose, ACCESS_TEAM_DOMAIN, ACCESS_AUD, ADMIN_EMAILS, AGENT_EMAILS
- (capability) CAP-14 docs and tooling follow-ups: identity-access, security (Access-bypass, header-spoofing, stolen-phone rows rewritten), api, data-model, deployment, free-tier-budget (D1 read per request, write per hour, quota residual), design (login + Agents pages); api-engineer, security-reviewer agents and add-api-route skill
- (constraint) no auth library, no slow hash: every secret (code, passphrase, session token) stored as HMAC-SHA-256 under AUTH_PEPPER; none stored or logged in clear; 10 ms CPU budget rules out PBKDF2 at safe iterations
- (constraint) users.email is primary key, lowercased, because prospects/visits/agent_positions key on email; no re-keying
- (constraint) zero cost (ADR-0002): no rate-limiting binding, D1 Free 5M reads/100k writes a day; quota exposure of anonymous /api requests
- (constraint) sync payload unchanged, clientVersion does not move; INVARIANT 5: a 401 never clears the outbox
- (constraint) app shell and admin chunk become public once Access goes; they must hold no data
- (constraint) migrations expand/contract; phase 1 runs with Access still in front; the owner or CI sets BREAK_GLASS/AUTH_PEPPER, never the repo or an agent (no wrangler secret)
- (constraint) before phase 3, check for a free WAF rate-limiting rule on /api/auth/*; if none, record the residual risk in free-tier-budget
- (constraint) follow-up docs each land in their own change (ADR consequences)
- (note) rotating AUTH_PEPPER invalidates every code, passphrase and session; accepted at four users; owner keeps BREAK_GLASS offline
- (note) non-goals: passkeys now (later additive kind), TOTP, user-chosen passwords and reset flow, emailed codes or sign-in links, signed cookie without sessions table, deleting users, rate-limiting binding

- (decision) Q1 resolved (walkthrough): admin passphrase is 20 Crockford base32 chars in 5 groups of 4 (100 bits); same alphabet and input normaliser as agent codes; no word list
- (decision) Q2 resolved (walkthrough): admin login form takes email + passphrase; lookup by users.email then hash compare; break-glass = OWNER_EMAIL + BREAK_GLASS in the same form; one generic error for wrong email or passphrase; reason: password-manager autofill needs a username field
- (decision) Q3 resolved (walkthrough): device label is automatic only, a parsed User-Agent summary (device family + browser, never the raw UA); sessions gains created_at; Agents page shows label + enrolled + last seen per user, enough to tell devices apart; no typed name; supersedes the assumption that the label might be typed
- (decision) Q4 resolved (walkthrough): one live code per user; generating a new code deletes that user's unused codes first; enrolling two devices is sequential
- (decision) Q5 resolved (walkthrough): a fourth À traiter row 'Prospects sans agent actif {n}' with Réassigner opening Prospects filtered to inactive agents; the deactivation dialog states how many prospects stay assigned; deactivated users leave the assign menu; changes the three-row À traiter rule in EXPERIENCE.md and docs/design.md
- (decision) Q6 resolved (walkthrough): a locked-out IP gets 429 with Retry-After; /login says 'Trop de tentatives depuis cette connexion. Réessayez à {heure}, ou changez de réseau.' and disables submit until then; a generic error would make a valid code look broken
- (decision) Q7 resolved (walkthrough): phase 2 ends when every active user has at least one live session; Agents page shows Inscrit / Pas encore inscrit per user; only then the owner revokes Access tokens and deletes the Access application; no JWT-fallback counter
