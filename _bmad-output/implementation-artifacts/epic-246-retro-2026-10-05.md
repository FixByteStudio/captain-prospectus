### Diff-scope review (inline lenses)

#### F1: a flagged place has no way to be fixed from the admin app (medium, behaviour + spec)

- **What happens.** A prospect flagged Hors cible is always `rejected` (`not_interested` → `rejected`, invariant 3). The Prospects row menu offers *Changer le statut* as its only edit, and it disables the current status (`RowMenu.tsx:58-68`). `changeStatus` is the only caller of `PATCH /prospects/:id` (`ProspectsScreen.tsx:239`, confirmed by #250 triage row 2). There is no field editor and no archive.
- **Observed on the local build.** After flagging a prospect, the only edit that clears the flag is a status change. `PATCH {"status":"new"}` unflagged it and left it **`new`, assigned to `agent@example.com`**: a closed restaurant, back in open statuses, assigned to an agent. I did not run the agent's Tournée to confirm it comes back onto the round.
- **Why it matters.** CAP-7's intent is "becomes a to-fix item for an admin" and its success text says "once an admin edits its fields or status". Fields cannot be edited from any screen, so the only exit is to reopen the place the agent said is closed.
- **Why the process missed it.** Row 2 of #250's triage saw that only status PATCHes exist and rejected the finding as a low edge on "any PATCH stamps". Done-when #4 tests the filter and the clearing rule, not whether an admin can resolve the flag with the screens that exist.
- **Disposition.** Fix now: an owner decision, then a story. See action items 1 and 2.

#### F2: a visit that syncs after an admin edit is never flagged (medium, spec, owner-accepted)

- **What happens.** The flag compares `out_of_target_reviewed_at <= visit.visited_at` (`admin.ts:622-640`). The owner decided on `visited_at`, not `received_at` (spec-gh-250 "Decided (2026-10-05)"), and triage row 1 documents the consequence.
- **Observed.** I PATCHed a prospect, then synced a visit dated two minutes earlier reporting `out_of_target`: it never appeared in `?outOfTarget=true` (total 0).
- **Why it still matters.** This is an offline-first app: a phone can hold a visit for hours. Any admin edit of that prospect in the meantime, such as a status change for another reason, makes the closed-place report invisible, with no trace. Nothing tells the admin the signal was lost.
- **Disposition.** Accept as-is (owner decision), restated as an open question. The upstream lesson is that an offline-first flag should compare against `received_at`; it stays the owner's call.

#### F3: the SPEC, the epic and the ticket still promise « Sans raison », which was dropped (medium, spec reconciliation)

- **What happened.** On 2026-09-30 the owner dropped the null bucket from the Visites filter: "There are no refusals from before #247, and the field asks for a reason since #248" (`407dd98`; PR #254 *Deviation from the ticket*; spec-gh-249 Auto Run Result, "Owner decision"). `reason=none` is now a 400 (`admin.test.ts:1465`, `export.test.ts:351`).
- **What is stale.**
  - `SPEC.md:34` (CAP-5), still frozen: "the 7 reasons plus 'Sans raison'".
  - `epic-refusal-reasons.md` Notes: "Assumption: 'Sans raison' in the Visites filter means …".
  - Story ticket #249 body and `story-visites-shows-and-filters-refusal-reasons.md` Verify line.
  - spec-gh-249's own Approach, I/O matrix, Code Map and Design Notes, which still describe `none`. Its Auto Run Result is the only place that says it was overridden. The #251 sweep left these as "build records".
- **The premise has a hole.** The owner's reason is "a filter for refusals with no stored reason matches nothing". CAP-3 promises the opposite: an old build keeps syncing, and its `not_interested` visit is stored with a **null** reason. I synced one live and it came back `refusalReason: null`. Any phone still on an older build after the deploy produces such rows. They show nothing in the ledger, are empty in the CSV, and no filter finds them.
- **Disposition.** Spec reconciliation, proposed (action item 3). Whether to bring the bucket back is the owner's call (open question 2).

#### F4: one unknown `refusalReason` blocks the whole sync batch (low, robustness)

- **What happens.** `refusalReason` is `z.enum`, so an unknown value is a 400 on the whole request. Observed live: `400 {"error":"validation","issues":[{"path":["visits",0,"refusalReason"],"code":"invalid_value"}]}`. The client treats any non-OK as `status: "error"` and keeps the outbox (`field/sync.ts:165`), so every other queued visit waits behind it and nothing is lost (invariant 5 holds).
- **Where this bites.** It needs a phone that sends a value the server does not know: a Worker rolled back below a newer build, or a future 8th reason shipped to phones before the server. #247's triage row 1 accepted it on "the SPA ships from the same Worker, so no newer build meets an older server".
- **Gap against the spec.** SPEC CAP-3 and its constraints say a missing reason, or one on another outcome, never refuses a visit. They are silent on an unknown value.
- **Disposition.** Defer. Add one sentence to the ordering rule in `docs/domains/prospecting.md`: a new reason value deploys the server first, and a rollback below a shipped build blocks sync. No code change proposed.

#### F5: the Hors cible predicate is unmeasured against the CPU budget (low, performance)

- **What the code shows.** `OUT_OF_TARGET_FLAGGED` is a correlated subselect run per candidate prospect, for the list and again for `total` (`admin.ts:622`). It runs only when the filter is on, and `last_visit_at is not null` prunes first. Index `visits_prospect_visited_idx` exists (`schema.ts:140`). #250 triage row 7 rejected it for that reason.
- **Not verified.** No `EXPLAIN` and no timing against the 300-place seed. Invariant 13 is 10 ms CPU per request, and open issue #102 is the same kind of unmeasured per-prospect statement.
- **Disposition.** Defer; fold into the measurement #102 already asks for.
