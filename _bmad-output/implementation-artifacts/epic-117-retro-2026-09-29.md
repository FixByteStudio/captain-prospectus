## Findings

### F1: the visit just recorded becomes the next stop again (high, behaviour)

- **What happens.** After "Enregistrer", the same prospect is still **"PROCHAIN ARRÊT 1"**, with a primary "Visiter" button and "Pas encore envoyé". The walking order comes from the agent's position, and the agent is standing at that door, so on a real device the visited stop is at about 0 m and comes out first by construction.
- **Sources.**
  - `src/client/field/TodayScreen.tsx:93` (`const [next, ...rest] = list.now`).
  - `src/client/field/today.ts`: `buildTodayList` flags `visitQueued` but never removes the stop or moves it out of `now`.
  - The live run in *Behaviour verification* below.
  - The spec accepted this on purpose: `spec-gh-118` triage row 23 says "the visited stop can be the card, and it must say it has not been sent".
  - A test locks it in: `TodayScreen.test.tsx:148`, "marks the next stop's card « Pas encore envoyé »".
- **What it breaks.**
  - EXPERIENCE.md Flow 1 climax (line 289): "Curry House is gone, … the next stop is Bar des Marolles".
  - Epic Done-when #1: "Flows 1 and 4 run end to end".
- **Disposition.** Fix now, once the owner has decided F2.

### F2: the UX contract contradicts itself, and a story settled it alone (high, spec)

- **The contradiction.** EXPERIENCE.md Flow 1 (line 289) says the stop is "gone". EXPERIENCE.md's own state table (line 182) and DESIGN.md › Stop row (line 387) keep it on the row with "Pas encore envoyé".
- **How it was settled.** `spec-gh-118` Design Notes (line 119) picked DESIGN.md, with this reason: "Hiding it client-side would mean deriving status from the outcome, which invariant 3 forbids." `docs/design.md:1253-1257` then made that a rule: the badge "never hides the stop … or moves it in the walking order (invariants 2, 3)".
- **Why the reason doesn't hold.**
  - Invariant 3 forbids the phone from *sending, showing or implying* the status an outcome leads to (CLAUDE.md; epic-117 context, "No status preview").
  - Taking a stop out of the walking order because *a visit to it is in the outbox* needs no outcome and no status. It uses the same read-only outbox fact the badge already uses (`today.ts`, `visitQueued` doc comment).
  - What invariant 3 does rule out is anything that differs *by outcome*. For example, hiding only "Pas intéressé" stops, or showing a "Refusé" look.
- **Disposition.**
  - This is a spec reconciliation for the owner to decide, not something to apply automatically.
  - **Upstream lesson:** a story that sets aside a flow named in the epic's Done-when should escalate to the owner, not settle it in its own Design Notes.

### F3: after the sync, the stop stays in the walking order with no marker (medium, limits the fix)

- **What happens.** "Intéressé", "Pas de contact" and "À relancer" all map to `follow_up` (`src/shared/constants.ts:62-68`), and `follow_up` is an open status (`:71`). The server's today list is "every open status" (`src/worker/routes/agent.ts:288-294`, `docs/domains/field-operations.md` › Today list). `next_visit_at` takes the visit's `follow_up_at` (`src/worker/routes/status.ts:54`), which is optional for "Intéressé" and "Pas de contact". So after the pull, the stop is back in `now`, now with no badge, and looks exactly like a stop nobody has visited.
- **Observed live.** After the sync the badge had gone, but Crêperie du Square was still "PROCHAIN ARRÊT 1".
- **Why it matters for the fix.** If only the before-sync state is fixed, the stop disappears on "Enregistrer" and comes back unmarked on the next sync. That is worse than today.
- **The fix needs a second fact that is not a status:** the prospect's `lastVisitAt`. It is already on the wire (`agent.ts:45`) and it is server truth.
- **Disposition.** Fix it together with F1.

### F4: the problem was caught once and routed only as a counting bug (medium, process)

- **What happened.** `spec-gh-119` triage row 1 (high, bad_spec) found that the stop "persists after the pull too — the inflation is not even transient". The amendment fixed only the progress denominator. `src/client/field/progress.ts:27-35` now documents the double-count workaround ("the round deliberately keeps a stop on the list after its visit is queued").
- **What was lost.** No issue was opened for the list behaviour itself, so it left the process at that point. #129, the only human check of Flow 1, is still open, so the contradiction never reached the owner.
- **Disposition.**
  - Process lesson: when a bad_spec finding is fixed only in part, the rest becomes a `found-in-passing` issue (CLAUDE.md › Stay in scope).
  - The epic's human-in-the-loop story came last, after 11 stories had built on the assumption. A Flow 1 walkthrough on the tracer bullet (#118) would have caught this.

### F5: nothing stops a second visit to a queued stop (low, adjacent risk; not exercised)

- **What the code shows.** The next-stop card keeps a primary "Visiter" on a stop whose visit is queued. `VisitScreen.tsx` has no check against `outboxVisits` (grep: no `visitQueued` or `outboxVisits` read).
- **Why it matters.** A second tap records a second visit for the same door. The server takes both, since each has its own UUID (invariant 4), and the admin sees two visits.
- **Not verified.** A double submission was not run.
- **Disposition.** Defer. The F1 fix removes the prompt that invites it.
