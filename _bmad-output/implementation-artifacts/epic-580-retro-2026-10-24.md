## Findings

### Going-in concerns: abuse of the code login

Verdict first: **no High or Medium finding; nothing found that lets a caller sign in without a valid code, learn a user's role, or spend a code twice.** The one item that needs the owner is F-G (S-1).

**S-1. F-G, evidence: an admin can mint an agent's code and sign in as the agent, and nothing records it.** *Confirmed in source. Owner decision; this retro does not take it.*
- **The path.** `POST /api/admin/users/:email/code` (`src/worker/routes/identity.ts:180`) sits behind `requireAdmin` (`src/worker/index.ts:97-99`). The target is any active user: the only filter is `WHERE email = ? AND active = 1` (`identity.ts:197`). The handler never reads `c.get("identity")`, so the minter is used for nothing. On the agent form (`src/worker/routes/auth.ts:123-154`) the code is bound to no email and no device; the session is created for `loginCodes.userEmail` with the agent's 90-day sliding lifetime (`session.ts:18-21`).
- **What the agent identity then reaches.** `requireAgent` (`index.ts:95`) is the only way an admin reaches `/api/agent/*`, since an admin D1 session gets 403 there. Sync, visits, field prospects, the position of the day and the numbered tournée are stamped with the agent's email. The visits look the same as the agent's own; the position is whatever the signing-in device sends.
- **What is recorded.** `login_codes` has `code_hash, user_email, created_at, expires_at, used_at` (`src/worker/db/schema.ts:381-394`): no minter. `sessions` has no "via code" or minter field. No route in `routes/identity.ts` or `routes/auth.ts` logs. A used code row is swept after `expires_at` (`src/worker/auth-sweep.ts:61`), so within 24 h at most. `DELETE /api/admin/sessions/:id` (`identity.ts:216`) leaves nothing behind.
- **The one trace.** A new device on that agent's row of Utilisateurs, with its creation time and a label parsed from the User-Agent (`identity.ts:64-85`), until it is revoked or expires. No route lists sessions to an agent, so the agent cannot see it.
- **Same cause, other direction.** One admin can mint a 1-hour code for another admin or for the owner and sign in as them. Both are admins, so the powers are equal, but the same lack of a record applies.
- **What the docs say.** Deliberate and silent on this use: `docs/domains/identity-access.md:24-26` and `:65` ("Generate a one-time code for any user, their own row included"); ADR-0029 decision 2; ADR-0038:43. ADR-0037's "an admin who canvasses uses an agent account" does not say whether that means someone else's. No hit for *audit*, *impersonat*, *on behalf*, *minted by* or *borrow* in ADR-0037, 0038, 0039, `identity-access.md` or `security.md`; the threat table (`docs/security.md:9-26`) has no insider row.
- **Costs of each way out, for the decision.** The data stage is disposable, so any schema change is one migration with no backfill.
  - *Accept and say so:* one line in ADR-0038 or ADR-0039 and one in `identity-access.md`; no code.
  - *Record the minter:* a `created_by` on `login_codes` that the spend copies to a column on `sessions`, shown on the device row; one migration, two statements touched, and the sweep already bounds the code rows' life.
  - *Restrict the target:* refuse minting for an agent's email, which removes the admin-assists-a-new-agent flow the docs describe (`identity-access.md:24-26`).

**S-2. Brute force: acceptable, and ADR-0039's figure re-derives.** *Confirmed in source.*
- A code is 8 Crockford characters from 5 random bytes, 2^40 (`session.ts:89-105`). Minting deletes the user's unused codes in the same batch (`identity.ts:193`), so there is at most one live code per user. Admin codes cannot match on the agent form (role is inside the spend, `auth.ts:138`).
- The throttle is 10 failures per fixed 15-minute window per IP (`login-throttle.ts:21`, `shared/constants.ts:290`), so 960 tries per IP per day. IPv6 counts by /64 and an IPv4-mapped address as its IPv4 (`login-throttle.ts:31-48`); a request with no `CF-Connecting-IP` shares one `unknown` bucket. The failure is reserved in one conditional upsert before the credential is read, so a parallel burst gets no more than 10 through.
- The agent form is not bound to an email, so a guess hits every live agent code: N live codes give N / 2^40 per try. With N = 2 and 10,000 IPs that is about 1.75 × 10⁻⁵ per day; N = 3 gives 2.6 × 10⁻⁵, which is ADR-0039's "about 3 × 10⁻⁵". The admin form needs a known admin email and its code lives 1 hour.
- **Limits worth knowing.** The throttle is per IP only; there is no global cap per window (the adversarial lens suggested one; ADR-0039 accepts the risk). The edge rate-limiting rule is dashboard setup that no test checks (`docs/security.md:17`). A hit enrols a device with a 90-day sliding session. Disposition: **accept**; numbers recorded so later retros stop re-deriving them.

**S-3. Email enumeration and role leak: none found.** *Confirmed in source and on a running Worker.*
- Every refusal is the same `unauthorized(REFUSED)`, 401, body `{"error":"unauthorized","message":"This code does not work."}`, no `Set-Cookie` (`auth.ts:44, 151`). The wrong-form, wrong-email, unknown-email, deactivated, expired, used and superseded cases all go through one batch of two statements.
- **Observed** on a local Worker (see Behavior verification): an agent's code on the admin form, an admin's code on the agent form, an admin's code with an agent's email, another admin's email and an unknown email all answered 401 with the same body and `content-length: 61`.
- **Timing.** When `OWNER_EMAIL` and `BREAK_GLASS` are both set, the *admin form* does two extra HMACs and a `timingSafeEqual` before the code path (`auth.ts:82-95`); the agent form never does. The extra work does not depend on the email typed, so it tells a timer which form it is talking to and that break-glass is configured; it reveals no user, role or active state. The old passphrase path equalised its work deliberately; this one does not. Disposition: **accept**, low.
- A malformed body is a 400, distinct from a 401, and says nothing about a user. Mint's 404 and 409 sit behind `requireAdmin`.

**S-4. Reuse, expiry and races: clean, with test gaps (V-3).** *Confirmed.*
- The role, the email, `usedAt IS NULL` and `expires_at > now` are in one conditional UPDATE; the session is inserted by an `INSERT … SELECT` guarded by `changes() = 1` in the same batch (`auth.ts:128-149`). Two logins racing on one code cannot both get a session; no spent code is left without a session. A refused code is not spent, so it still works on the right form.
- `expires_at == now` is refused (`auth.ts:136`), pinned by `auth.test.ts:397-401` for an agent. The expiry is stored at mint; a later change of `LOGIN_CODE_TTL_MS` cannot touch a live code. `SESSION_TTL_MS` and `LOGIN_CODE_TTL_MS` are used in separate places; no mix-up.
- Deactivating a user deletes their sessions and unused codes in the same batch (`identity.ts:156-163`); a code minted for a user deactivated meanwhile is refused (409 on mint, 401 on spend).

**S-5. Invariants 10 and 13 hold on the sign-in route.** *Confirmed in source; CPU not measured.*
- Invariant 10: identity comes from `identityFromSession`, a join of `sessions` and `users` on the token HMAC that takes the role from `users` (`src/worker/auth.ts:102-140`); `DEV_USER_EMAIL` is honoured on localhost only and needs an active row. Break-glass can only be reached on the admin kind with the exact `OWNER_EMAIL`.
- Invariant 13: the HMAC key import is cached in module scope (`session.ts:29-44`). Per request: agent form, success, 3 HMACs and 3 D1 round trips (throttle upsert, the two-statement batch, the refund); admin form with break-glass configured and a refusal, 5 HMACs and 2 round trips. Nothing in the diff adds work beyond the earlier passphrase path. The CPU figure itself was not measured.

**S-6. Throttle trade-offs, deliberate.** Anyone sharing an IP (carrier NAT, an office, one IPv6 /64) with an agent can lock that agent out for up to 15 minutes by failing 10 times (`login-throttle.ts:79-85`; ADR-0029 decision 8). A 400 counts as a failure too: two malformed requests of mine on a fresh local database used up part of the bucket. Disposition: **accept**.

**S-7. A 24-hour code can outlive the admin cap through break-glass.** *Confirmed by reading; narrow.* The TTL is chosen from the target's role at mint (`identity.ts:190`) and the spend re-checks the role but not the lifetime (`auth.ts:138, 147`). No route changes a role (`userUpdateSchema` allows `active` only), but break-glass upserts `role: admin` on the owner's row (`auth.ts:101-105`). If `OWNER_EMAIL` was first created as an agent and holds an unused 24 h code, break-glass promotes it and that code opens an admin session for up to 24 h instead of 1. This is the same hole as F-A (roles fixed at creation, break-glass the one writer), so it rides on that decision. Disposition: **defer to F-A**.

**S-8. Break-glass is a permanent, unlogged way in.** *Known, ADR-0029 decision 7.* A leaked `BREAK_GLASS` is an admin with no record and no expiry until the owner rotates it; the code enforces no minimum strength (`docs/deployment.md:40` says `openssl rand -hex 32`); sign-ins by break-glass are refunded from the throttle and logged nowhere. ADR-0038 already says the owner keeps it offline and rotates it if seen. Disposition: **accept**.

### Diff-scope review: Worker and shared

**D-1. The code dialog shows only a time of day for a 24-hour code.** *Confirmed; caused by PR #626, found independently by four lenses.* `CodeDialog.tsx:43` renders `t.validUntil(formatBrusselsTime(issued.expiresAt))` and `copy/admin.ts:96` words it « Valable jusqu'à {heure}, une seule fois. »; `formatBrusselsTime` returns "HH:MM" only (`src/client/format.ts:49`; `format.test.ts:194` expects "15:24"). `docs/design.md:1367` specifies the same. **D-2. **D-3. Break-glass and a code share the admin form's refusal sentence.** « Le code a peut-être expiré ou déjà servi : demandez-en un nouveau » (`copy/field.ts:268-269`) also answers a wrong break-glass secret. Deliberate (one sentence whichever part was wrong, spec-gh-610). **Accept.**
