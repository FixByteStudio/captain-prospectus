### Diff-scope review: Worker and shared

**F-A. Break-glass is a second writer of `users.role`, so "roles are fixed at creation" has an exception.** *Confirmed in source.* Three lenses found it independently (adversarial W1, edge-case E5, security F2). Owner decision.
- `src/worker/routes/auth.ts:98-107`: `onConflictDoUpdate({ target: users.email, set: { role, active: true } })` with `role = "admin"`. The comment says it puts "a deactivated or demoted owner back". That line was kept by the later admin-code-login epic.
- If `OWNER_EMAIL` names an existing agent, whoever holds both break-glass secrets turns that agent into an admin. Their assigned prospects drop off the roster, and their outbox gets 403 on every sync. It also bypasses the last-admin guard (`identity.ts:144-152`).
- It needs two operator-held secrets, so it is a configuration risk, not a remote one. No test pins the choice either way; the #593 tests cover PATCH only.
- **Lesson:** a story that makes a value immutable lists every writer of it (grep the column) in its spec.

**F-B. Admin 403 was proven only through the `DEV_USER_EMAIL` bypass.** *Confirmed.* Fix now (action 3).
- `src/worker/sync.test.ts:1043, 1051, 1451, 2124` set `env.DEV_USER_EMAIL = "admin@example.com"`; no test sends an admin D1 session cookie to `/api/agent/*`.
- I ran that probe in a scratch copy (Behavior verification): the 403 holds with a real session. The gap is the missing committed test, not a hole in the code.

**F-C. A 403 from `/api/agent` now has two sources, and the docs and one comment still say one.** *Confirmed.* Fix now (action 4).
- `docs/domains/identity-access.md:76`: "A 403 at sync is read as a 401 (its only source is the cross-origin check)". `src/client/field/sync.ts:43`: "403 is only the cross-origin check". `requireAgent` also answers 403 (`src/worker/auth.ts:201-212`).
- Behaviour is as ADR-0037 intends (the client keeps the outbox); the text is stale.

**F-D. A prospect PATCH that re-sends the assignee it already has is refused when that assignee is off the roster.** *Confirmed on the server, API only.* Accept.
- `src/worker/routes/admin.ts:1106-1113` runs `unknownAssignee` whenever `assignedTo` is present, not when it changes. A prospect still assigned to a pre-epic admin, with a PATCH that carries the same `assignedTo` plus another field, gets 400 and nothing is written.
- The admin client sends `assignedTo` only through bulk assign (`ProspectsScreen.tsx:230-232`), so no screen reaches it.

**F-E. The Done-when 2 grep is enforced by nothing.** *Confirmed.* Fix now (action 3).
- `eslint.config.js:34` has only `no-restricted-globals`; CI (`.github/workflows/ci.yml`) runs lint, test and `check:precache`. Reintroducing an admin branch on the field side passes every check unless it changes tested behaviour.
- The state today is clean.

**F-F. Pre-epic data is stranded, and the epic only counts it.** *Confirmed.* Accept (disposable stage).
- Prospects already assigned to an admin are not migrated. `NO_ACTIVE_AGENT` counts them (`admin.ts:772-776`), they are bulk-reassignable, and no agent's sync pull sees them. Old admin visits stay in the totals but in no agent row. `/agents/:email/round` answers 404 for an admin (`admin.ts:179`), so old admin positions are never read.
- Nothing in the release path (S-4) covers these rows.

**F-G. An admin can mint a login code for an agent.** *Confirmed in source; documented; open question.*
- `POST /api/admin/users/:email/code` (`src/worker/routes/identity.ts:180-210`) serves any active user ("the admin's own row included"); `identity-access.md:65` and ADR-0038 say the same on purpose. After the code, the admin signs in on the agent form and has agent identity: visits, tournées and positions land under the agent's email, and nothing records which admin minted the code.
- `requireAgent` is not bypassed, but ADR-0037's "an admin who canvasses uses an agent account" is silent on borrowing someone else's.
- The route and its docs predate the epic. The security review rates it Low. See Open questions.

Reported and **not** raised as findings after reading the source: the check-then-write race on assignment (a deactivation between the roster read and the UPDATE leaves the prospect on a non-roster agent, which "sans agent actif" surfaces); the second 403 body (`routes/agent.ts:340-342`, « Ce prospect ne vous est pas assigné. ») that tests cannot tell from the role 403; `requireAgent` being `role !== "agent"` (fine with two roles); the dev seed writing an assignee and a position with no role check (`routes/dev.ts:103-105, :250`, local only, #597). `requireAgent` and `requireAdmin` read the identity from the D1 session join, never a header (`auth.ts:112-127, 189-212`).
